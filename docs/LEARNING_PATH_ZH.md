# 简历排序项目：学习与面试路线

这是 AI 辅助开发的个人原型。公司提出需求、代码完成、离线评估和公司上线是
四个不同的事实。只有亲自理解和验证的部分，才适合在面试中作为自己的技术判断。

## 学习顺序

1. 业务与标注：读 `ats_benchmark/README.md`，定义“比当前 ATS 好”的具体含义。
   练习：给一个岗位写三条可由简历证据判断的要求，明确“缺少信息”如何处理。
2. 基线：读 `evaluate.py::BM25Index`。手算一个查询对三份文档的排序。
   解释词频、文档频率、长度归一化；为什么关键词方法可能胜过小型神经网络？
3. 表示学习：读 `dataset.py` 和 `models.py`。跟踪一段文本的 token、embedding、
   attention pooling、归一化和余弦相似度；说明128-token截断的风险。
4. 训练：读 `train.py`。解释 ListNet 的标签从哪里来、辅助损失做什么、
   为什么合成技能标签不等于招聘经理的相关性判断。
5. 混合检索：读 `hybrid.py`。手算 RRF；解释为何不直接相加 BM25 与余弦分数，
   为何必须用 validation 选择权重，为什么允许最终选择纯 BM25。
6. 工程：运行 API 与 `rank_documents.py`。追踪同一个 query 的离线与在线结果；
   测试空文本、未知ID、重复候选人、失效模型配置和并发请求。
7. 评估：读 `ats_benchmark/evaluate.py`。手算 NDCG、Precision、池内 Recall；
   解释为什么 bootstrap 的单位是岗位而不是候选人，以及漏标为何使结论不可靠。

## 真实技术案例记录格式

每次亲自完成实验后填写：现象 → 假设 → 最小复现 → 修改 → 前后测量 → 限制。
记录 commit、命令、数据版本、随机种子、硬件和失败尝试。不要先编一个成功故事。

当前可以学习的已发现问题：

- 原数据流程只有 train/test，缺少用于选择融合权重的 validation。
- 训练使用的 epochs 与 checkpoint 内保存的配置可能不一致。
- 全 padding 文本在 attention softmax 中会产生 NaN，现改为明确报错。
- 神经模型与 BM25 分数尺度不同，现提供 validation-selected RRF。
- 不同候选人池或没有人工标注，不能证明新系统比 ATS 更好。
- 旧延迟数字来自小规模顺序/并发 smoke test，不代表持续生产负载。

## 面试追问练习

- 经理说“ATS不好”，你如何把意见变成可测量的问题？
- 只有被录用的人有反馈，你的训练标签有什么选择偏差？
- 模型 Recall@10 很低，是否一定不好？候选池有多少相关人？
- 你怎样避免同一岗位的改写文本跨越 train 和 test？
- 混合模型没有提高 NDCG，你会部署它吗？为什么？
- 候选人把JD关键词复制进简历，会出现什么问题？如何检验？
- 离线 NDCG 提高，能否说招聘质量提高？还缺哪些证据？
- 从3,000份到300万份简历，索引、刷新、内存、延迟各会如何改变？

开始正式模拟面试前，请能不看代码画出数据流程，并现场解释一次失败实验。
不要说自己已在公司处理过300万份简历；这可以作为系统设计讨论。
